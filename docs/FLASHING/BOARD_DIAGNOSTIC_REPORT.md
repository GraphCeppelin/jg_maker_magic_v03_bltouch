### 3.2 Размер flash — КЛЮЧЕВОЕ подтверждение (§6)

## 4. Разбор `1E 98 01` vs `1E 98 21` — главное объяснение

**Пара сигнатур (известная «путаница» у Microchip):**

| MCU | Signature | Flash |
|-----|-----------|-------|
| ATmega1280 | `1E 98 01` | 128 KB |
| ATmega2560 | `1E 98 21` | 256 KB |

Оба чипа разделяют первые два байта `1E 98`; различаются **третьим** (`01` vs `21`).

**Что мы измерили:**
1. Сигнатура через USB-bootloader: **`1E 98 01`** (стабильно 2 раза).
2. Размер flash: **261 426 B ≈ 255 KB** → **только ATmega2560** (1280 не может).
3. Успешная запись+верификация прошивки **173 KB** → **только 256 KB**.

**Вывод (обоснованно):**
- По **двум независимым физическим фактам** (размер flash и ёмкость прошивки) кристалл — **ATmega2560**. Это ground truth.
- Сигнатурное `1E 98 01` — **аномалия чтения третьего байта через конкретный USB-bootloader/CH340-канал** (на некоторых платах и прошивках Optiboot/avr-gcc bootloader'ов сигнатурное чтение через USB даёт «1280-совместимый» третий байт, либо в avrdude.conf/путь `wiring` подменяется). Это **не означает**, что чип — 1280: физическая ёмкость flash это опровергает.
- **Практическое значение: нет.** Для нашей прошивки (`-p atmega2560`) и для записи всё работает корректно (подтверждено flash size и верификацией). На будущие операции запись идёт как `atmega2560` и проходит успешно.

> **Формулировка для отчёта:** «Сигнатура читается как `1E 98 01`, однако чип однозначно ATmega2560 — подтверждено размером flash (261 426 B ≈ 255 KB) и ёмкостью прошитой прошивки (173 KB). Расхождение в третьем байте сигнатуры — артефакт чтения через USB-bootloader, не свидетельствует о смене чипа и не влияет на корректность прошивки.»

## 9. АКТИВНАЯ ДИАГНОСТИКА: `x_min: TRIGGERED` (2026-09-22)

**Симптом:** после загрузки D3/PE5 (X_MIN) периодически читается TRIGGERED (pin LOW) даже без нажатого выключателя. Состояние **меняется само по себе** во времени — признак **активной** тяги LOW, а не пассивного короткого замыкания.

### 9.1 Матрица изоляции (cable-state matrix)

| # | Состояние кабелей | После | `x_min` | Вывод |
|---|-------------------|-------|---------|-------|
| 1 | все X-кабели + BLTouch | boot | **open** (1 раз, при инициализации) | pullup платы работает |
| 2 | все X-кабели + BLTouch | boot, +несколько секунд | **TRIGGERED** | что-то тянет LOW ПОСЛЕ boot |
| 3 | 10-pin каретки **вынут** | reboot | **open** ✓ | 10-pin или его соседи виноваты |
| 4 | BLTouch **вынут** (Z+ и Z−) | reboot | **TRIGGERED** × 6 reads (12 с) | **BLTouch-цепь НЕ единственная причина** (или X-кабель был вставлен — см. §9.4) |

**Ключевой факт пользователя:** «открыто было только первый раз при инициализации платы» → активный драйвер включается после старта MCU (BLTouch-клоны с MOSFET-выходом в OD-режиме, или элемент на плате).

### 9.2 Установленные факты (code audit, verified grep)

- В этом форке **D3/PE5 используется ТОЛЬКО как `X_MIN_PIN`** (никакого другого `X_MIN_PIN`/переопределения, `SERVO3_PIN 4` = D4, не D3).
- `PE5_PWM = &OCR3CL` — D3 это OC3C Timer3: если где-то активен Timer3-CCTA PWM, порт мог стать OUTPUT. В Marlin 2.0.5.4 Timer3 обычно не используется (не подтверждено M43).
- `endstops.cpp`: при `ENDSTOPPULLUPS` init делает `SET_INPUT_PULLUP(X_MIN_PIN)` — open при отключённых кабелях это подтверждает.
- M45 в сборке **нет**; инспекция пинов — **M43**, только с `PINS_DEBUGGING` (сейчас закомментарен в `Configuration_adv.h` ~строка 3142).
- `M42 P3 S255` для форсинга HIGH **ЗАПРЕЩЁНО**: при наличии короткого замыкания на GND через вывод AVR пойдёт ~300 mA — риск вывода/трека.

### 9.3 Безопасные правила (согласовано)

1. **НЕ форсить D3 HIGH** (M42) без снятия внешних кабелей — риск повреждения вывода MCU.
2. Измерения **только DC-напряжение на живом питании** (мультиметр на входе MCU не шунтирует) или **сопротивление при ОБЕСТВОЕННОЙ** плате. Сопротивление «12–17 Ω в диапазоне 200 кΩ» под нагрузкой — **бессмысленно** (мультиметр вгоняет тестовый ток в живую цепь).
3. Все изменения `Configuration.h` / `Configuration_adv.h` — **только с явного разрешения пользователя**.
4. `M112` не использовать; только power-cycle.

### 9.4 ЧЕКЛИСТ СЛЕДУЮЩИХ ШАГОВ (для пользователя)

> **ВАЖНО:** перед каждым M119 явно фиксировать состояние кабелей. Неоднозначность «что вставлено» уже дважды испортила интерпретацию (строки 1–4 выше).

Чек-лист (✅ вставлен / ❌ вынут):
- [ ] X− 3-pin (конец каретки, D3 signal)
- [ ] 10-pin кабель каретки
- [ ] X+ коннектор (filament runout, D4)
- [ ] Y− (D14)
- [ ] Z− BLTouch (D18)
- [ ] Z+ BLTouch servo (D19)

**План A — полная изоляция D3:**
1. Вынуть **ВСЕ** кабели X (X− 3-pin, 10-pin, X+) и BLTouch (Z+, Z−).
2. Power-cycle (выкл/вкл питания).
3. Через ~15 c: `m119_loop.ps1` (6 reads / 12 с).
   - **open × 6 стабильно** → D3 на плате чист, виноват внешний кабель → включать обратно по одному (сначала X− 3-pin, M119; потом 10-pin, M119; потом X+, M119; потом Z+, M119; потом Z−, M119) → найдём конкретный кабель.
   - **TRIGGERED** (хотя бы 1 из 6) → **активный элемент на самой плате** вокруг PE5 → перейти к Plan B.

**План B — PINS_DEBUGGING / M43 (нужно разрешение пользователя):**
1. Разкомментировать `#define PINS_DEBUGGING` в `Marlin/Configuration_adv.h` (~строка 3142).
2. Пересобрать: `wsl -e bash -lc "cd /mnt/f/git/jg_maker_magic_v03_bltouch/Marlin && make -j16 ARDUINO_INSTALL_DIR=/home/vivakalman/Arduino HARDWARE_MOTHERBOARD=1020"`
3. Прошить: `powershell -NoProfile -ExecutionPolicy Bypass -File "$env:TEMP\flash_final.ps1"`
4. Через COM4: `M43 P3 I` — читаем:
   - `PIN MODE: Input` + `Input: 1` → всё чисто на уровне MCU → внешний драйвер.
   - `PIN MODE: Input` + `Input: 0` при ВСЕХ кабелях вынутых → **повреждение входа MCU** (реже) или активный pull-down на плате (транзистор/опторазвязка) → ремонт/замена платы.
   - `PIN MODE: Output` / `PWM: ON` / `COM3C: enabled` → firmware/OC3C конфликт → искать Timer3 users.
   - `M43 P3 O` — самодиагностика (Marlin сам циклично дёргает пин, читаем `Input` при `Output: HIGH`/`LOW`).
