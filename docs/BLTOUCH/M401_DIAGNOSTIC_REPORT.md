**Дата:** 2026-09-19 · **Жёсткие ограничения соблюдены:** без G28/G29, без осей, без нагрева, без M500, без изменений конфигурации и прошивки.

## 2. OBSERVED BEHAVIOR

- Игла двигается по командам S10/S90; при включении делает самотест (наблюдено пользователем).
- `M401` — **нестабильно**: один прогон прошёл чисто (F2), другой — с `busy` и финальным STOW (F3).
- В неудачном прогоне `M119` шёлся **во время** выполнения `M401` (ответ `busy: processing`) — т.е. `M401` был в длительном recovery (clear() ≈ 4×750 мс), а не в простом deploy.
- `M280 P0 S160` перед тестами — всегда снимает состояние.

## 3. MARLIN EXECUTION TRACE (этот исходник)

**M401:**
```
GcodeSuite::M401 (M401_M402.cpp:34)
 → probe.deploy() → BLTouch::deploy_proc() (bltouch.cpp)
   → _deploy_query_alarm():  MOVE_SERVO(0,10) → safe_delay(750) → READ(Z_MIN)
       ├── open     → success, pin остаётся DEPLOYED
       └── triggered → clear(): RESET→STOW→DEPLOY→STOW (каждая 500–750 мс)
                       → повторный _deploy_query_alarm()
                       ├── open      → success
                       └── triggered → "BLTouch failed" + stop()
```

**M280 P0 Sxx:** `M280.cpp:44` → `MOVE_SERVO(0, xx)` → **конец**. Никаких READ, никакого recovery.

**M119:** `endstops.cpp:422` → `_set_SW_mode()` (S60, delay 500) → вывод `READ(Z_MIN) != Z_MIN_ENDSTOP_INVERTING` → `_reset_SW_mode()`: **`if (triggered()) _stow(); else _deploy();`**

**Вывод по M119 (критично):** если на момент M119 игла DEPLOYED, clone отдаёт triggered → M119 **сам втягивает её** (STOW). Если игла STOWED и не сработана — M119 **сам выдвигает её** (DEPLOY). M119 — НЕ безобидный reader: он переключает физическое состояние пина.

## 4. ELECTRICAL INTERPRETATION

- Линия Z-S **реально переключается** (F5): при нажатии `TRIGGERED`, при отпускании `open` → не является постоянно замкнутой/плавающей.
- Internal pull-up включён (F7) → плавучий вход в idle не обязан висеть в triggered-уровне.
- **НЕ выполнено (нужен мультиметр, пользователем):** измерение `Z-S → Z-G` в 5 состояниях (stowed / reset / deployed / pressed / stow) и `J1-V → J1-G` (USB-only vs сетевое, + просадка при движении пина). До выполнения — уровни остаются *выведенными по M119*, а не измеренными.

## 5. ROOT CAUSE (локализовано до уровня поведения датчика; внутренняя причина НЕ доказана)

> **Status: most-likely, not proven.** Мы НЕ измеряли отдельный физический признак ALARM (мультиметром/осциллографом) на clone. Доказано: (a) линия Z-S переключается (F5), (b) явный `S160` до DEPLOY надёжно снимает сценарий (F4, F2), (c) путь M401 при triggered-read заканчивается STOW (F3, §3).

**Наиболее вероятная причина: clone периодически попадает в состояние, при котором после DEPLOY вход Z-MIN читается как TRIGGERED; явный `S160` до DEPLOY надёжно снимает этот сценарий.** Внутренняя причина этого состояния (ALARM clone vs иная причина, дающая тот же уровень на момент чтения) — **ещё не разделена**: измерения `Z-S→Z-G` и просадки +5 V из §4 не выполнены.

**Усилитель: F9 (побочный эффект M119)** — M119 сразу после M401 физически стовит выдвинутую иглу.

Цепочка неудачного прогона:
1. К моменту `M401` clone был в состоянии, при котором после DEPLOY вход Z-S читается как triggered (накоплено предыдущими командами, в т.ч. M119 SW-mode переключениями — F9). Внутренняя природа этого состояния не доказана.
2. `M401` → DEPLOY → READ = triggered → `clear()` (RESET→STOW→DEPLOY→STOW).
3. В окне восстановления сигнал снова читался как triggered → повторный DEPLOY снова «alarm» → `stop()` + **финальное состояние STOW**.
4. Пользователь видит: «M401 ничего не сделал / игла не выдвинута». На самом деле M401 выполнил DEPLOY→recovery→STOW.
5. Отдельный усилитель: `M119`, отправленный сразу после `M401` (F9), при deployed-игле **сам её стовит** — скрывает факт, что deploy первоначально был успешен.

Почему после `M280 P0 S160` всё стабильно: явный RESET **до** deploy гарантирует выход из alarm; в `deploy_proc()` RESET идёт только **после** неудачи, и у clone не остаётся окна, чтобы снять состояние до первого READ.

## 6. WHAT IS NOT THE CAUSE (исключено доказательствами)

| Версия | Статус |
|---|---|
| A. питание (в целом) | не подтверждено как причина: полный цикл работает, saмотест работает; просадка при движении — **ещё не измерена** (см. §4) |
| B. распиновка 3-pin | исключено: S10/S90/S160 дают ожидаемые механические реакции |
| C. полярность 2-pin | исключено: trigger двунаправлен (F5) |
| D. плохой trigger-сигнал | исключено: open/triggered переключается детерминированно (F5) |
| E. плавающий Z-S | маловероятно: pull-up включён (F7), линия стабильно открыта в idle |
| F. неверный OD/5V mode | исключено как причина: OD + internal pull-up корректно детектирует оба уровня (F5); менять на S140 **не нужно** |
| H. слишком раннее чтение (BLTOUCH_DELAY=500) | **опровергнуто**: окно deploy = `BLTOUCH_DEPLOY_DELAY=750` (F8), `BLTOUCH_DELAY` его не управляет. «Delay 500→1000» не чинил бы наблюдаемое |
| I. баг recovery-логики M401 | нет: логика штатная и отработала в матрице (F2) |
| J. дефект именно Marlin 2.0.5.4 | не подтверждено: путь идентичен эталонному |
| K. defect of the clone (including internal ALARM) | **most likely, but NOT proven as an internal state** — only behavior is proven: S160 clears the scenario (F2, F4) |

## 7. IMMEDIATE FIX (без перепрошивки)

Рабочий протокол (подтверждён 2 прогонами):
1. Перед любым deploy/homing:
   ```gcode
   M280 P0 S160
   ```
2. Далее `M401` или `G28` (при штатном питании и установленном датчике).
3. **Не шлать `M119` сразу после `M401`** — M119 сам переключает пин (F9). Для проверки состояния после deploy: подождать 1 с, затем `M119` осознанно, понимая, что при triggered он стовит.
4. Если при G28 ошибка BLTouch → повтор: `M280 P0 S160` → `G28`.

## 8. FIRMWARE FIX NEEDED? — **NO (пока)**

Протокол §7 закрывает проблему. Перепрошивка не требуется.

### Формулировка «проблема локализована»
Поведение локализовано: когда clone находится в состоянии, при котором после DEPLOY вход Z-S читается как triggered, `M401` делает DEPLOY → recovery RESET→STOW→DEPLOY→STOW → повторный READ снова triggered → stop()+STOW, и пользователь видит «игла не выдвинулась». Доказано: явный `M280 P0 S160` перед M401 даёт 100% прохождение матрицы (F2, F4). Внутренняя причина этого состояния (ALARM clone vs иная) — **не доказана**; нужны измерения `Z-S→Z-G` и просадка +5 V (§4, pending).
